# Controlled synthetic drift and candidate demonstration

This guide describes the current notebook and the callable workflow used by the Model Orchestrator button. The experiment is isolated from genuine-label retraining. It demonstrates distribution-shift detection, candidate training, same-row comparison, and a recommendation within an explicitly synthetic setup.

## What the experiment uses

`notebooks/drift_detection_simulation.ipynb` documents the workflow; `src/retraining/drift_simulation_workflow.py` implements the callable run. The workflow reads the existing V2 Parquet dataset as a source of feature rows, but deliberately does **not** load its `isFraud` labels. It samples source rows without replacement from the chronological V2 windows (steps 1–422, 423–565, and 566–743), keeping source IDs disjoint. The latest saved run sampled 30,000 training rows, 12,000 validation rows, and 20,000 test-feature rows from bounded pools.

New labels are generated by a demonstration rule:

```text
simulated isFraud = (amount >= training-source 80th percentile) XOR type_TRANSFER
```

In the latest saved run the amount cutoff was approximately 245,047.944. The test labels are created only after training and threshold selection. This generated rule is not an investigative label source and does not represent real fraud behavior.

The experiment compares 100,000 reference feature rows from the V2 training window with 20,000 later-window feature rows using the existing PSI, KS/proportion-test, and Benjamini–Hochberg detector. It then trains a separate XGBoost candidate using the frozen 34-feature contract, validation-selects the candidate threshold, and compares V2 and the candidate on identical held-out features with labels generated by the same synthetic rule.

## Artifacts and safety boundary

Each invocation creates a unique report directory under `reports/drift_simulation/<run-id>/` and candidate directory under `models/drift_simulation/<run-id>/`. The report directory includes the simulation configuration and split, drift report/feature table, candidate evaluation, V2 comparison, recommendation, final integrity summary, and figures. The candidate is saved separately as `simulation_candidate.json` with metadata, threshold and training report.

The run verifies before/after V2 artifact hashes, confirms V2 remains the resolver-selected active model, checks that the real orchestrator run inventory did not change, records that no genuine verified labels were used, and records `automatic_promotion: NO`. The notebook/callable workflow is not the real candidate-training route and does not submit labels, update the Stage 2 or Stage 3 stores, train from genuine labels, modify V1/V2 artifacts, or activate/promote its candidate. Do not point the real activation manifest at these artifacts.

The separate `src/retraining/simulation_demo.py` (Stage 6) is another synthetic demonstration. It samples historical PaySim `isFraud` labels, which are still simulator-generated rather than genuine outcomes, and writes its audit/candidate under `reports/simulation_demo/`. The older `src/retraining/stage6_demo.py` writes a bounded demo bundle under `models/candidates/stage6_demo/`. These are distinct from the controlled drift simulation above and remain marked ineligible for genuine promotion.

## Run behavior

The Model Orchestrator page has an explicit **Run Simulation Demonstration** button, which calls `run_simulation()`. The run requires the project data/artifacts and NumPy, Pandas, PyArrow, XGBoost, scikit-learn, and Matplotlib. It writes new unique candidate/report directories. Running it is intentionally not a read-only health check.

No notebook execution or simulation run is required to inspect the checked-in evidence. For report locations and lifecycle distinctions see [project results and limitations](PROJECT_RESULTS_AND_LIMITATIONS.md), [Stage 6](STAGE6_RETRAINING_DEMONSTRATION.md), and [the project workflow](PROJECT_WORKFLOW.md).
